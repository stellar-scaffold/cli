# Frontend: clients and `app-lib`

Every official template (React and Svelte) shares one framework-agnostic package, `@stellar-scaffold/app-lib` in `app-lib/`. Framework-specific code lives in `app/`. Read `app/CLAUDE.md` (`app/AGENTS.md` in newer projects) for its routes, providers and stores.

## Generated clients

`stellar scaffold build --build-clients` (run by `npm run dev`) writes, for the selected network:

- `app-lib/clients/<name>/`: a TypeScript **binding** package per contract, generated by `stellar contract bindings typescript`. It holds the contract's types and a `Client` class.
- `app-lib/clients/index.ts`: one configured **client** per contract, exported under the camelCase contract name from `scaffold.yml` and bound to that network's RPC URL, passphrase, and deployed contract ID.

Import clients from the index, never from the binding packages:

```ts
import { guessTheNumber, myToken } from "@stellar-scaffold/app-lib/clients"
```

Both directories are regenerated on every build. To add behavior, wrap a client in a module under `app/` and import that.

A contract appears in `index.ts` only if it lists the network you built for in `scaffold.yml`. Code that imports a contract that doesn't exist on some network fails to typecheck when you build for that network. That is intentional: it catches calls to contracts that aren't deployed there.

## Calling contract methods

Methods and arguments mirror the Rust contract: same `snake_case` names, arguments passed as one object. Rust integer types of 64 bits and wider (`u64`, `i128`, `u128`, `u256`) are `bigint` in TypeScript; `Address` is a `G…`/`C…` string; `Option<T>` is `T | undefined`; `Result<T, E>` becomes a `Result` with `isOk()`, `isErr()`, `unwrap()`, `unwrapErr()`.

Every call returns an assembled transaction that has already been **simulated**.

**Read-only calls**: use the simulated result. No wallet, no fee.

```ts
const { result: admin } = await guessTheNumber.admin()
```

**State-changing calls**: pass the signer's address as `publicKey`, then sign with the connected wallet and submit.

```ts
import { signTransaction } from "@stellar-scaffold/app-lib"

const tx = await guessTheNumber.guess(
  { a_number: BigInt(guess), guesser: address },
  { publicKey: address }, // required: clients are created without a default source
)
const { result } = await tx.signAndSend({ signTransaction })
if (result.isErr()) {
  console.error(result.unwrapErr()) // the contract's error enum
} else {
  console.log(result.unwrap())
}
```

If a call needs another account's authorization (for example a `require_auth` on an address other than the source), inspect `tx.needsNonInvokerSigningBy()` before `signAndSend`.

To get a client's contract ID (for event subscriptions or explorer links), read `guessTheNumber.options.contractId`.

## `@stellar-scaffold/app-lib`

| Export | What it does |
|---|---|
| `connectWallet()`, `disconnectWallet()`, `profileModal()` | Stellar Wallets Kit modals. On `LOCAL` and `FUTURENET` only wallets that support custom networks are offered (Freighter, xBull, Hana) |
| `signTransaction` | Pass to `signAndSend` |
| `onWalletChange(cb)` | Subscribe to `{ address, networkPassphrase }`; fires immediately and on connect, disconnect, or wallet network switch. Returns an unsubscribe function |
| `getWalletNetwork()` | The network the wallet reports, if it supports reporting one |
| `fetchBalances(address)`, `MappedBalances` | Horizon balances keyed by asset |
| `fundAccount(address)`, `getFriendbotUrl(address)` | Friendbot funding on local, testnet and futurenet |
| `subscribeToEvents(contractId, topic, onEvent, pollInterval?)` | Poll RPC for a contract's events; returns a stop function |
| `network`, `stellarNetwork`, `networkPassphrase`, `rpcUrl`, `horizonUrl` | The app's network, from `PUBLIC_STELLAR_*` in `.env` |
| `networkStatus(...)`, `NetworkState` | Compare the wallet's network with the app's (`ok`, `mismatch`, `disconnected`, `unverified`) |
| `shortAddress(addr)`, `formatNetworkName(name)`, `labPrefix()` | Formatting, and Stellar Lab link prefix |
| `@stellar-scaffold/app-lib/styles.css` | Shared base styles |

The templates wrap the wallet state for their framework: React has `useWallet()` (from `app/src/hooks/useWallet`), returning `address`, `balances`, `isPending`, `signTransaction`, and `updateBalances`; Svelte has readable stores `address`, `balances`, `isPending`, `networkPassphrase` plus `signTransaction` and `updateBalances()` in `app/src/lib/stores/wallet`. Use these in components rather than calling `onWalletChange` again.

## Network consistency

The CLI bakes the network's passphrase, RPC URL, and contract IDs into `index.ts` for the network it built (`STELLAR_NETWORK`). The app connects using `PUBLIC_STELLAR_NETWORK`, `PUBLIC_STELLAR_NETWORK_PASSPHRASE`, `PUBLIC_STELLAR_RPC_URL`, and `PUBLIC_STELLAR_HORIZON_URL`. If they point at different networks, every call fails with a missing contract or a passphrase mismatch. Change both together, then restart `npm run dev` so Vite picks up the new `.env`.

## Building the app

```bash
npm run build --workspace app   # typecheck + Vite production build; there is no root `build` script
```

Build the clients for the production network first (`stellar scaffold build --build-clients --network mainnet`, with the `.env` `PUBLIC_*` values set for mainnet), so `index.ts` holds the production contract IDs.
